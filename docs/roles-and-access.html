Роли и права доступа

Как разведены два уровня прав — клиент/владелец магазина и суперадмин платформы: где хранится роль, что реально её проверяет (UI, edge-мидлварь, RLS в Postgres), а что проверяет только для вида.

01 Две роли

Роль — это одно текстовое поле в одной таблице. Всё остальное построено поверх него.

Роль пользователя хранится в profiles.role и принимает одно из двух значений: client (по умолчанию, обычный владелец магазина) или admin (суперадмин платформы). Триггер, создающий профиль при регистрации, всегда проставляет client — подменить это значением из метаданных при signUp() нельзя, роль назначается только напрямую в базе. Готового интерфейса для выдачи прав администратора в приложении нет.

На клиенте роль превращается в булево значение isSuperAdmin — оно вычисляется один раз при загрузке сессии и пересчитывается при каждой смене состояния авторизации, сбрасываясь в false при выходе. Само по себе это значение ничего не защищает — это просто удобный флаг для рендера интерфейса; реальные границы описаны в разделах 5 и 6.

02 Модель владения магазином

Владение — это внешний ключ, а не роль.

shops.owner_id ссылается на auth.users(id) — обычная одиночная FK-колонка без ограничения уникальности. Из этого следует:

  • у одного магазина — ровно один владелец (или NULL, хотя намеренно так никто не выставляет);
  • один аккаунт может владеть несколькими магазинами — поэтому в приложении всегда есть выбор «текущего» магазина, а не просто «магазин пользователя».

owner_id выставляется равным id текущего пользователя только при создании магазина — форма настроек намеренно не отправляет это поле при сохранении уже существующего магазина. Суперадмину экран создания магазина недоступен напрямую — попытка открыть его с параметром «новый магазин» перенаправляет в раздел клиентов суперадминки, где создание организовано иначе.

owner_id дополнительно защищён на уровне самой базы: триггер на UPDATE принудительно возвращает старое значение этого поля независимо от того, что пришло в запросе. Это защита не столько от злонамеренного клиента (RLS и так решает, кому вообще разрешён UPDATE), сколько от собственных багов приложения — например, если форма где-то случайно отправит это поле при сохранении чужого магазина, смены владельца всё равно не произойдёт. Единственный способ сменить владельца — прямое обращение к базе в обход триггера; отдельного пользовательского флоу «передать магазин» в приложении нет.

03 Четыре уровня защиты

Не все уровни одинаково настоящие. Это стоит проговаривать явно в любом проекте с ролями — иначе легко принять UI-скрытие кнопки за реальную защиту.

Отдельно: /api/widget/* публичны и не аутентифицированы намеренно — их вызывает виджет с чужого сайта без входа пользователя, это не пробел.

04 UI-уровень

Три компонента формируют то, что видит пользователь — ни один из них не может быть единственной защитой, потому что весь их код уже загружен в браузер.

СостояниеЧто видно в боковом меню
Суперадмин, магазин не выбранКлиенты / Промпты AI / Тарифы
Суперадмин, зашёл в магазин («Войти»)Полное меню владельца — как у обычного клиента
Владелец, активный магазинДашборд / История / Товары / Аналитика / Биллинг / Настройки
Владелец, магазин заблокированТолько Биллинг
Владелец без магазинаТолько «Создать магазин»

ShopContext определяет, какие магазины вообще видны: суперадмин получает все строки, которые пропускает RLS-политика на shops (то есть все), обычный пользователь — запрос дополнительно фильтруется по owner_id = user.id уже на клиенте, хотя RLS всё равно перепроверит это на сервере независимо от того, что отправил браузер.

Блокировка по неактивной подписке (redirect на биллинг, скрытие разделов) целиком снимается для суперадмина одной строчкой в начале проверки — суперадмин никогда не видит на себе последствия блокировки чужого магазина, даже «зайдя» в него.

05 Edge-мидлварь

Первая настоящая граница — раньше, чем страница вообще начинает рендериться.

Мидлварь перехватывает каждый запрос к путям /admin/* и /superadmin/*: если сессии нет — редирект на главную; если путь начинается с /superadmin — дополнительно читается profiles.role для этой сессии, и при значении, отличном от admin, снова редирект. Это реальная серверная проверка, а не то же самое, что клиентский layout-компонент, который тоже редиректит, но только после того, как JS-бандл страницы уже загрузился.

Область действия важна: список путей мидлвари покрывает только сами страницы (/admin/*, /superadmin/*), но не API-роуты под /api/admin/* — это два разных префикса, и совпадение по маске одного не означает совпадение другого. См. раздел 8.

06 RLS в Postgres

Вторая настоящая граница — единственная, которая работает независимо от того, через какой клиент пришёл запрос.

Все политики сводятся к одной из двух форм: owner_id = auth.uid() (или тот же вывод через цепочку внешних ключей — например, для изображений товара это product_id → products.shop_id → shops.owner_id) для владельца, и public.is_admin() — для суперадмина, объединённых через OR. Обе формы проверки роли, инлайновая и через функцию, встречавшиеся в разных таблицах по историческим причинам, приведены к единственной — вызову is_admin() — чтобы определение «кто такой админ» существовало в проекте ровно в одном месте.

ТаблицаДоступ владельцаДоступ суперадмина

products, product_imagesтовары своих магазиновтовары всех магазинов

Проверка роли, которая не проверяет себя саму

Проверка admin-доступа вынесена в отдельную SQL-функцию is_admin(), а не написана как inline-подзапрос прямо в политике. Причина не стилистическая: если политика на таблице profiles сама содержит подзапрос SELECT role FROM profiles WHERE id = auth.uid(), Postgres обнаруживает, что политика читает ту же таблицу, которую защищает, и это триггерит бесконечную рекурсию — запрос падает с ошибкой независимо от того, что реально пытался прочитать пользователь.

Решение — обернуть проверку в функцию с модификатором SECURITY DEFINER: такая функция выполняет свой внутренний запрос от имени владельца функции, минуя RLS, поэтому обращение к profiles изнутри неё не запускает те же политики повторно. Политика после этого просто вызывает public.is_admin() вместо того, чтобы инлайнить подзапрос — рекурсия невозможна в принципе, а не просто маловероятна.

Это общий паттерн, не специфичный для этого проекта: любая RLS-политика, которой нужно свериться с ролью или правами того же пользователя через ту же (или связанную с самоссылкой) таблицу, рискует получить точно такую же рекурсию. SECURITY DEFINER-функция — стандартный обход.

07 Возможности суперадмина

Сводка того, что доступно только с ролью admin.

  • Тарифы — полный CRUD над глобальной таблицей тарифов (создание, редактирование, архивирование, удаление); обычный владелец только выбирает тариф из списка.
  • Промпты AI — редактирование единственной строки платформенных настроек: модель и текст промпта для генерации, модерации и классификации, общие для всей платформы.
  • Клиенты — список всех магазинов платформы с возможностью включить/выключить любой из них и «войти» в панель управления любого магазина как если бы это делал его владелец.
  • Ручные операции биллинга — активация любого тарифа любому магазину с произвольным количеством начисляемых примерок (без автоматического расчёта) и начисление бонусных примерок без оплаты. Обе операции реализованы как SQL-функции, которые сами проверяют is_admin() внутри себя и потому единственные из всех функций, изменяющих баланс, выданы роли authenticated напрямую — все прочие похожие функции (продление тарифа, начисление пакета) остаются доступны только сервисной роли, потому что не содержат такой проверки и слепо доверяют переданному shop_id.

Каждая такая операция пишет в transactions.performed_by id вызвавшего её администратора — колонка служебная, в интерфейсе нигде не отображается, нужна только чтобы при появлении более одного администратора можно было поднять из данных, кто именно выполнил конкретное действие.

Этот же паттерн — SECURITY DEFINER + проверка is_admin() в начале тела функции + выдача authenticated вместо service_role — стоит использовать для любой новой операции, которую должен выполнять администратор напрямую из браузера, а не через доверенный серверный процесс.

08 API-роуты

Мидлварь не покрывает /api/admin/* (её маска — /admin/*, другой префикс), поэтому каждый такой роут отвечает за проверку сам.

РоутПроверка
/api/admin/billing/renew-subscriptionsсекретный ключ в query-параметре (крон)
/api/admin/products/sync-allсекретный ключ в query-параметре (крон)
/api/admin/shops/validate-feedпроверка сессии
/api/admin/products/syncсессия + владение магазином через RLS-запрос к shops
/api/admin/products/analyzeсессия + владение магазином через RLS-запрос к shops
/api/admin/shops/upload-logoсессия + владение магазином через RLS-запрос к shops, затем бизнес-правила (активный платный тариф)
/api/widget/*намеренно публично, без входа — ключ доступа это сам shop_id

Проверка владения в последних трёх роутах не дублирует логику вручную, а переиспользует уже существующую RLS-политику на shops: запрос выполняется тем же клиентом, что несёт куки сессии пользователя (не сервисным ключом) — если политика не пропускает эту строку, значит и действие с этим магазином не разрешено, будь то попытка чужого владельца или анонимный запрос без сессии вовсе. Сама привилегированная операция (синхронизация фида, AI-анализ, загрузка файла) после этой проверки по-прежнему выполняется через сервисный ключ. Крон (sync-all) на эту проверку не завязан — он вызывает библиотечную функцию синхронизации напрямую, в процессе, а не ходит на /api/admin/products/sync по HTTP.

Отдельного пространства /api/superadmin/* в проекте нет — все действия суперадмина идут либо напрямую в Supabase из браузера (и упираются в RLS/is_admin()), либо через две RPC-функции из раздела 7.
